# HUD Theme manifest schema

**File:** `manifest.schema.json`
**Draft:** [JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12/schema) (`$schema` is set explicitly in the file).
**`$id`:** `https://assets-4gy.pages.dev/registry/schemas/1.0/manifest.schema.json`
**Schema version:** `1.0` — co-frozen with [HUD Theme Contract 1.0](../../docs/architecture/HUD_Theme_Contract_1.0.md) at the Plan §5 hard gate 2 (Story #3, alongside Story #4).

This is the machine-readable descriptor every HUD Theme's `manifest.json` MUST conform to. It is a **plain JSON Schema** — `type`, `enum`, `pattern`, `properties`, `required`, `if`/`then`/`else`, `allOf`/`anyOf`, `contains` — nothing here is a bespoke keyword, so it is consumable unchanged by `ajv` (used by this repo's own tests), any other draft-2020-12-compliant validator, and downstream build/runtime/Playground tooling per the AC.

## Where the prose authority lives

**`docs/architecture/HUD_Theme_Contract_1.0.md` §3 and §27 are the prose authority.** This schema is generated by hand against that document (mainly its §27 "Handoff to #3" section, which gives the field table, sub-object shapes, and the ~14 cross-field validation rules almost verbatim). Where this schema and the Contract disagree, **the Contract wins** until this schema is revised (Contract §3, first paragraph of §3).

If you're trying to understand *why* a field looks the way it does, read the Contract section cited in that field's `description` (every property in the schema carries one), not this README.

## `schemaVersion` vs `contractVersion` vs Theme `version` (Arch §30–31)

These are three **independent** version axes (Contract §3.2):

| Axis | What it tracks | Owned by |
|---|---|---|
| `schemaVersion` (manifest field) | Which `manifest.schema.json` **shape** a manifest conforms to | This file — bumped only when the manifest's structure changes |
| `contractVersion` (manifest field) | Which HUD Theme Contract **major** the Theme targets | `HUD_Theme_Contract_1.0.md` — a Contract MAJOR bump is a breaking change (§24.3) |
| `version` (manifest field) | The Theme's **own** SemVer release | Each Theme, independently, over many releases |

A Theme can ship many `version` releases while never touching `schemaVersion` or `contractVersion`. This schema file's own `$id` carries its version (`.../1.0/manifest.schema.json`); a future breaking schema change ships at a new `$id` path (e.g. `.../1.1/...` or `.../2.0/...`) rather than mutating this one in place, so a manifest can always name exactly which schema shape it was authored against.

## What the schema enforces structurally vs what the test suite enforces semantically

Most of Contract §27.8's ~14 cross-field rules **are** expressible in plain JSON Schema (`if`/`then`, `contains`, nested `const`s) and are encoded directly here — see the `allOf` block at the end of the file and the inline `description`s. A few rules reference **dynamic keys across two different array/object fields** (e.g. "every slot name is either one of the ten standard names, or the `name` of some entry in `customSlots[]`", "an external host is on the §16.2 allowlist OR justified by *some* `knownDeviations` entry") that plain JSON Schema cannot express without either giving up `additionalProperties: false` enforcement elsewhere or reaching for non-standard keywords. Per the Story #3 brief, those are wired into this repo's Vitest suite instead (`tests/helpers/semantics.js`, exercised by `tests/unit/manifest.schema.test.js`), not into the schema file. The schema file itself never needs a bespoke keyword to pass validation with any standard tool.

Rules encoded directly in the schema (non-exhaustive): the removed `ratios`/`aspectRatios` rejection (via top-level `additionalProperties: false`), `variants`/`orientations` must equal their full 1.0 sets, `compositions` has exactly the 6 fixed `<variant>:<orientation>` keys, the three mandatory-`true` compositions, the `maxi:portrait` supported-or-deviation escape hatch, `entrypoints` keys matching supported compositions exactly, the closed `dataSource.providers` enum, the closed `knownDeviations[].code` enum, the `baseVersion` exact-or-caret pattern, and the `engine=svg` + (`skyViewer`|`dataSource`) ⇒ `isolation=scoped-root` rule.

Rules left to the test suite: `slots.required ∩ slots.optional === ∅` and the standard-or-`customSlots`-registered check; `externalResources[].host` / `capabilities.dataSource.hosts[]` / `capabilities.mediaEmbed.hosts[]` allowlist-or-deviation check; `dataSource.hosts` corresponding to the *declared* `dataSource.providers` (not just any allowlisted dataSource host); `capabilities.modes.default` being one of `capabilities.modes.values`.

## `engine` includes the reserved values — this is deliberate, not a loophole

`engine` is a 5-value enum: `svg`, `css`, `video`, `static`, `gadget`. The Contract is explicit and repeated on this point (§5.1 table, §5.2, §19.1 checklist, §27.1 field table): `video`/`static`/`gadget` are **valid, schema-accepted, reserved-but-unsupported** enum values — a manifest declaring one of them is **schema-valid**, so Themes can be authored/listed ahead of Runtime support; a 1.0 Runtime that is asked to *mount* one fails at runtime with `RendererUnsupported` (§20), and publication/validation tooling **MUST warn**, not reject (§19.1: "if video|static|gadget → WARN (no 1.0 Runtime)"). This schema does not reject them, and `tests/helpers/semantics.js` models the WARN as a non-blocking `warnings[]` entry (see `fixtures/valid/reserved-engine-warning.json`). **See "Contract gaps flagged" below** — this is called out because it diverges from the Story #3 issue's own "Validation semantics" wording, which is stale on this point.

## Contract gaps flagged for the owner

Two places where the frozen Contract is internally inconsistent, found while encoding §27 literally. Neither was resolved unilaterally — see the Coder report on Story #3 for the recommendation in each case:

1. **HUD-10 / `maxi:landscape` deferral.** §8.5, §22.3 (`no-maxi-landscape` code) and §25.4 describe a portrait-native Theme (HUD-10) deferring `maxi:landscape` symmetrically to how a landscape-native Theme defers `maxi:portrait`. But §27.1's field table and §27.8 rule 4 only grant the supported-or-deviation escape hatch to `maxi:portrait` — `maxi:landscape` (like `mini:landscape` and `micro:portrait`) is listed as unconditionally `supported: true`, with no stated exception. This schema follows §27 literally (no escape for `maxi:landscape`), since §27 is the section explicitly written as this schema's handoff. The `fixtures/valid/hud-10.json` fixture ships **both** `maxi:landscape` and `maxi:portrait` as `supported: true` to stay valid under this reading, rather than modelling the §25.4 narrative's landscape deferral.
2. **No `knownDeviations` code for "external host outside the §16.2 allowlist."** §16.2 says a non-allowlisted host "MUST be declared in `externalResources[]` **and** justified by a `knownDeviations` entry," but §22.3's closed code enum has no code meaning that specifically (it only has `no-maxi-portrait`, `no-maxi-landscape`, `external-io-on-mount`, `shadow-dom-fallback`, `shared-base-host-selectors-stripped`) — and §19.3 says an *unrecognised* code fails validation. As written, a Theme with a legitimately deviant host cannot name a valid code for it. `tests/helpers/semantics.js` works around this with a best-effort heuristic (any `knownDeviations` entry whose `scope`/`note` names the host, or scopes to `"all"`) rather than a specific code match, and flags the gap here rather than inventing a new recognised code unilaterally.

## Vision §8 / Architecture §11 example manifests are pre-reframe and do not validate — by design

Both examples (`hud-07` / "Orbital Scanner") predate the 2026-09-09 orientation-model reframe recorded in Contract §1.4: they use the removed `aspectRatios` field, string-valued `entrypoints` keyed by exact ratio (`"mini:16:9": "mini/16x9/hud.svg"`), and omit fields this Contract makes REQUIRED (`contractVersion`, `baseVersion`, `orientations`, `compositions`, `isolation`). Contract §3.3 is explicit that a manifest containing `ratios`/`aspectRatios` **MUST fail validation** — so making this schema accept the Vision/Architecture examples would mean contradicting the frozen Contract to satisfy two illustrative, non-normative sketches from documents one and two versions behind the Contract they predate. This schema does not accept them; instead, `tests/fixtures/valid/hud-01.json` reproduces the Contract's own §3.14 example verbatim (which does validate), and `hud-02.json`/`hud-03.json`/`hud-10.json` model the Contract's own §25 baseline cross-check tables. See the Coder report on Story #3 for the full reasoning.

## Running the fixture corpus

```sh
npm install
npm test
```

`tests/fixtures/valid/` — manifests that MUST validate (structurally and semantically), modelled on HUD-01, HUD-02, HUD-03, HUD-10, a bare-bones minimal Theme, and a reserved-engine (`video`) Theme (schema-valid, semantic-layer warning).
`tests/fixtures/invalid/` — manifests that MUST fail **schema** (`ajv`) validation, one per structural rule.
`tests/fixtures/semantic-invalid/` — manifests that are schema-valid but MUST fail the **semantic** layer in `tests/helpers/semantics.js`.
